Guia do Picoshell

O picoshell executa uma cadeia de comandos conectados por pipes — é o | do shell. Você recebe um array de comandos e precisa ligar a saída de cada um na entrada do próximo, executando todos em paralelo.

Você terminou o projeto quando…

  • Para cada comando (exceto o último), chama pipe(fd) antes do fork().
  • No filho: se não for o primeiro, dup2(in_fd, 0) — redireciona stdin para a saída do cano anterior.
  • No filho: se não for o último, dup2(fd[1], 1) — redireciona stdout para a entrada do cano atual.
  • No filho: fecha os fds brutos não usados e chama execvp (com exit(1) de fallback).
  • No pai: fecha fd[1] (escrita do cano atual) — sem isso o leitor nunca vê EOF.
  • No pai: fecha in_fd antigo e guarda fd[0] no in_fd para a próxima iteração.
  • while(wait(&status) > 0) coleta todos os filhos e retorna 1 se qualquer um falhou.

A assinatura: desvendando char **cmds[]

O tipo parece intimidador mas é um array (terminado em NULL) de arrays de strings — exatamente o que o execvp espera como segundo argumento.

char *cmd1[] = {"/bin/ls", NULL};
char *cmd2[] = {"/usr/bin/grep", "picoshell", NULL};
char **cmds[] = {cmd1, cmd2, NULL};

// No loop:
//   cmds[i]    → array de strings do comando i (char **)
//   cmds[i][0] → nome do executável             (char *)
//   cmds[i+1]  → NULL se for o último comando
Por que char **cmds[] e não char ***cmds?

São equivalentes como parâmetro de função. char **cmds[] deixa claro que é um array de char **; char ***cmds é um ponteiro para char **. Dentro da função o compilador trata os dois da mesma forma.

As syscalls: pipe, fork, dup2, execvp, wait

SyscallO que fazRetorno
pipe(fd) Cria um cano bidirecional. fd[0] = ponta de leitura, fd[1] = ponta de escrita. Tudo o que for escrito em fd[1] pode ser lido em fd[0]. 0 ok · -1 erro
fork() Duplica o processo. Pai e filho continuam a partir do mesmo ponto. Todos os fds abertos são copiados para o filho — incluindo os criados com pipe(). 0 no filho · PID no pai · -1 erro
dup2(a, b) Faz o fd b apontar para o mesmo recurso que a. Se b estava aberto, fecha-o primeiro. Usado para redirecionar stdin (b=0) ou stdout (b=1). b ok · -1 erro
execvp(cmd, argv) Substitui a imagem do processo pelo programa cmd. O processo herda todos os fds abertos — inclusive os configurados com dup2. Só retorna se falhar. só -1 (erro)
wait(&status) Bloqueia até que qualquer filho termine. Preenche status. Retorna -1 quando não há mais filhos. Por isso o loop é while (wait(&status) > 0). PID do filho · -1 se nenhum
WIFEXITED(s) Verdadeiro se o filho saiu normalmente, sem sinal. int (bool)
WEXITSTATUS(s) O código de saída do filho — o valor passado para exit() ou retornado por main(). Só válido se WIFEXITED for verdadeiro. int
fork() copia tudo — e isso importa

Quando o pai chama pipe(fd) e depois fork(), o filho herda fd[0] e fd[1]. Pai e filho têm ambas as pontas abertas. Fechar a ponta de escrita no pai e no filho (depois do dup2) é obrigatório para que o leitor veja o EOF no momento certo.

Como o dup2 redireciona stdin e stdout

// Antes: fd 0 (stdin) aponta para o teclado
//        fd[0] (ex: fd 3) aponta para a leitura do Cano 1

dup2(fd[0], 0);  // fd 0 agora aponta para o Cano 1 (substitui teclado)
close(fd[0]);    // fecha fd 3 (desnecessário — fd 0 já faz o mesmo papel)

// Agora: qualquer read() em fd 0 vem do cano, não do teclado

O padrão in_fd: a variável que liga as iterações

in_fd começa como 0 (o fd do teclado) e, após cada iteração, passa a guardar a ponta de leitura (fd[0]) do cano recém-criado. É o fio condutor que conecta um processo ao próximo.

Por que fechar fd[1] no pai?

Após o fork(), a ponta de escrita do cano (fd[1]) existe tanto no filho quanto no pai. O leitor (próximo filho) só recebe EOF quando todos os descritores de escrita daquele cano são fechados. Se o pai não fechar fd[1], o leitor espera para sempre.

Por que fechar in_fd no pai?

Após o dup2(in_fd, 0) no filho, o fd original (in_fd) não é mais necessário no filho — e também não é no pai. Fechar no pai evita vazamento de descritores. Se o pai guardar a leitura de todos os canos abertos, o próximo cano pode ter problemas de EOF também.

O código completo e anotado

#include <unistd.h>    // fork, execvp, pipe, dup2, close
#include <sys/types.h> // pid_t
#include <sys/wait.h>  // wait, WIFEXITED, WEXITSTATUS
#include <stdlib.h>    // exit

int picoshell(char **cmds[])
{
    /* in_fd começa com 0 (stdin do teclado).
     * Ao final de cada iteração, recebe fd[0] do cano criado nela. */
    int i = 0, in_fd = 0, fd[2], pid, status;

    while (cmds[i])
    {
        /* Cria o cano ANTES do fork. O fork copiará fd[] para o filho.
         * A condição curto-circuita: pipe() só é chamado se houver
         * um próximo comando. */
        if (cmds[i + 1] && pipe(fd) < 0)
            return 1;

        if ((pid = fork()) < 0)
            return 1;

        if (pid == 0)   /* ── BLOCO DO FILHO ──────────────────── */
        {
            /* Redireciona stdin para a ponta de leitura do cano anterior.
             * Pula no primeiro comando (in_fd == 0 == teclado). */
            if (in_fd != 0)
            {
                dup2(in_fd, 0);  // fd 0 agora lê do cano anterior
                close(in_fd);    // fecha o fd bruto (desnecessário)
            }

            /* Redireciona stdout para a ponta de escrita do cano atual.
             * Pula no último comando (sem próximo → stdout vai pra tela). */
            if (cmds[i + 1])
            {
                dup2(fd[1], 1);  // fd 1 agora escreve no cano atual
                close(fd[0]);    // filho não lê deste cano
                close(fd[1]);    // fd bruto desnecessário (dup2 cuidou)
            }

            execvp(cmds[i][0], cmds[i]);
            exit(1);  // execvp só chega aqui se falhar
        }
        /* ── BLOCO DO PAI ───────────────────────────────────── */

        /* Fecha o in_fd antigo: o filho já tem sua cópia via dup2.
         * Pula no primeiro comando (in_fd == 0 = teclado, não fechar). */
        if (in_fd != 0)
            close(in_fd);

        /* Prepara in_fd para a próxima iteração:
         * fecha a escrita (CRUCIAL — sem isso o leitor nunca vê EOF)
         * e guarda a leitura para passar ao próximo filho. */
        if (cmds[i + 1])
        {
            close(fd[1]);   // fecha escrita do cano no pai
            in_fd = fd[0];  // guarda leitura para a próxima iteração
        }
        i++;
    }

    /* Coleta todos os filhos. wait() retorna -1 quando não há mais.
     * Retorna 1 se qualquer filho não saiu normalmente ou saiu com erro. */
    while (wait(&status) > 0)
        if (!WIFEXITED(status) || WEXITSTATUS(status))
            return 1;
    return 0;
}
Por que exit(1) e não return 1 após o execvp?

Se execvp falha (executável não encontrado), o filho precisa sair. Com return 1, o filho voltaria para o while e começaria a criar mais fork()s — um desastre. exit(1) garante que o filho termina no lugar.

Armadilhas comuns

  

    
ErroConsequênciaCorreção

    
      

        Não fechar fd[1] no pai após o fork
        O cano nunca fecha para o leitor (pai ainda tem a escrita aberta). O próximo filho espera por mais dados para sempre. O programa trava.
        close(fd[1]) no bloco do pai, dentro do if (cmds[i+1]).
      

      

        Não dar exit(1) após execvp
        Se execvp falha, o filho retorna ao loop e começa a fazer seus próprios fork()s — fork bomb em potencial.
        Sempre colocar exit(1); logo após execvp().
      

      

        Chamar pipe() antes de verificar se cmds[i+1] existe
        Cria um cano para o último comando, que nunca é usado. Vaza dois fds.
        if (cmds[i + 1] && pipe(fd) < 0) — a condição curto-circuita.
      

      

        Não fechar in_fd no pai
        O pai acumula descritores de leitura de todos os canos anteriores. Em pipelines longos, pode exceder o limite de fds do processo.
        if (in_fd != 0) close(in_fd); logo antes de atualizar in_fd.
      

      

        Não fechar fd[0] e fd[1] no filho após o dup2
        O filho passa os fds brutos para o programa executado. Geralmente inofensivo, mas tecnicamente incorreto — o programa filho vê fds extras que não deveria.
        close(fd[0]); close(fd[1]); depois do dup2(fd[1], 1).
      

      

        Usar wait() fora do loop (só uma vez)
        Coleta apenas um filho. Os outros ficam como zumbis. Se o filho coletado não foi o único com erro, o código de retorno pode estar errado.
        while (wait(&status) > 0) — coleta todos os filhos um a um.
      

      

        Testar pid == 1 (do pai) em vez de pid == 0 (do filho)
        O bloco de redirecionamento roda no processo pai. O filho recebe o PID do pai como retorno de fork() e entra no bloco "errado".
        No filho fork() retorna 0, sempre: if (pid == 0).
